# ADR 0013: Contract 1.3 — archive and merge, tags, first-class longlist/shortlist, search brief, commercial records

Status: ACCEPTED (2026-10-29, architect) · Extends ADR 0002 (lifecycles), 0005 (audit), 0006 (REST), 0009 (erasure), 0010 (views, bulk), 0011 (candidate pool). Contract: `contracts/openapi.yaml` 1.3.0, `contracts/schema.md`, `contracts/events.md`.

## Context
The data manipulation matrix (`docs/product/brand/app-architecture.md` §f) leaves **M** cells that block live searches: no archive or restore, no client merge, no tag management, no rank or rationale on longlists and shortlists, no brief, no fee agreement or placement, no audited export. Requirements v2 marks the matching items Must (SX-001/003/008/009/013/014/019/020/021/022/025, PB-007/008/009/011/014/018/019/021, CO-013/014/019/020/021). Build tasks D1-D8 and D11 need one contract so db, backends and frontends can work in parallel.

## Decision
1. **Archive = soft delete with restore** on `account`, `person`, `job_order` (proposal archive, proposal exports and `conflict_check.proposal_id` are cut from 1.3 in the review round: proposals move to opportunities in R7/R75; the 1.2 proposal endpoints stay as they are): `archived_at`, `archived_by`, `archive_reason` (`ArchiveReason`), `archive_note`; `POST .../archive` and `.../restore`; lists take `archived` (default false = the 1.2 result). Archived records reject changes with the new 409 `ARCHIVED`. Guards: account without open job orders, job order and person without active applications. Archiving a person is **not** erasure; ADR 0009 stays the only erasure path. Audit = Envers on the columns plus timeline `ARCHIVE` and `ArchiveStateChanged`.
2. **Account merge** (`POST /accounts/{id}/merge`, MANAGER/ADMIN) is orchestrated by `accounts`; pipeline rows move through the synchronous SPI `AccountMergeParticipant` in the same transaction. The merged account is never deleted (FKs to `account` stay `no action`): it is archived with reason `MERGED` and `merged_into_id`, plus an `account_merge` row and `AccountMerged`. Not reversible.
3. **Tags stay arrays** on the four records (ADR 0010). `tag_definition` adds colour, description and the talent-pool flag (a talent pool is a flagged tag; no new entity). Rename, merge and delete are set-based rewrites with `version + 1` and **no per-record Envers revision** (tags are not personal data); pipeline follows through `TagChanged`.
4. **Longlist/shortlist without touching `PipelineStage`**: `CandidateList` is derived (`PipelineStage.candidateList()`: SOURCED/SCREENED = LONGLIST, client-facing stages = SHORTLIST, REJECTED = none). `application` gains `rank` (gapless per job order and list, kept by the service under a job-order row lock, no unique index), `rating` 1-5, `rationale`, `outreach_status`. Entering the shortlist needs rating and a rationale of at least 20 characters (409 `TRANSITION_GUARD_FAILED` with `errors`). `PUT /job-orders/{id}/ranking` sets a whole list. Client feedback is per application and round; DECLINE closes the application (REJECTED).
5. **Evaluation** lives in `pipeline` (`candidate_evaluation` with scores as jsonb against `search_criterion`, `interview_note`, `candidate_reference`), keyed by person with an optional job order. Private notes and referee details never reach reports.
6. **Search brief** is a 1:1 `search_brief` row plus `search_criterion` (soft-removed, never deleted, because scores refer to them), `job_order_team_member` and `target_company`. The compensation band is encrypted at rest with `FieldCipher` like person pay (R73: it reveals what the client pays); read access is unchanged. The brief also records `team_size`. Missing brief fields warn, never block (SX-001). Approaching an off-limits target company reuses the `OFF_LIMITS` guard and manager override.
7. **Commercial records in `pipeline`**: `agreement` (framework terms per account, engagement per job order; status is a plain field, not an ADR 0002 lifecycle), `fee_schedule_item` with `FeeTrigger` and `InvoiceState` (the platform records invoices, never issues them), `placement` (one per application, compensation encrypted with `FieldCipher`, fee computed from the agreement, manager-only override) and an append-only `conflict_check` log that stores no person names. `PlacementCreated` makes accounts add a GUARANTEE_PERIOD off-limits rule. Review round (R67): `agreement` gains the signed PDF (`signed_file_id`, `PUT/GET /agreements/{id}/signed-file`) and `guarantee_start_basis`; each fee item has `vat_applies`. `placement.person_id` and `application_id` are `on delete set null`, so fee and guarantee records outlive an erased person (compensation and status reason are nulled).
8. **Account profile fields** (legal name, tax id, tax office, MERSIS, e-invoice, billing, parent account, group name, size band, HQ country, confidentiality level, language) are plain strings without validation rules in 1.3; `missingForActive` lists what an active client still lacks.
9. **Pool search**: `skills`, `function_area`, `seniority` on `person`; filters on `GET /people`. The salary filter is applied **in memory after decryption** (max 5,000 rows, only rows whose compensation the caller may read) so field encryption (ADR 0011) is not weakened by a plaintext salary column.
10. **Exports and reports**: `POST /exports` replaces client-side CSV for audited exports (threshold 25 rows for people and accounts, manager approval, watermark, 24-hour expiry, no free text stored); `ExportSource` SPI per entity. Client reports are generated PDFs stored per job order; exposure (channel REPORT) is written when a report is marked sent, not when generated. Import gets column mapping and a 30-day rollback that archives what the batch created.

11. **Organisation identity (R63, review round).** `account` becomes the organisation table **in place** (no rename: every FK, Envers table, API path and the frontend keep working). It gains role flags `is_client`, `is_prospect`, `is_target`, `is_employer` (`OrganisationRole` in the API as `roles`), `aliases text[]` and a generated `normalized_name` (accents, punctuation and legal forms removed by the immutable SQL function `normalize_org_name`), unique among non-archived rows; this replaces the unique `lower(name)` index. `parent_account_id` stays the group tree. `person_employment.organisation_id` (nullable FK) links an employment to an organisation while the free-text `company` stays as the fallback. Off-limits rules on an organisation can `include_subsidiaries`. Matching is one function (`OrganisationApi.match`: normalised name or alias, single hit only) used by import, employment entry, target companies and off-limits, so companies are matched once at import. `status` stays the client lifecycle; `sector` is required only for CLIENT/PROSPECT. New endpoints use the word *organisation*; existing paths stay `/accounts`. `GET /accounts` without `role` returns CLIENT/PROSPECT, so the 1.2 client list does not fill up with employers.
    - Alternatives: a new `organisation` table with `account` as a client extension (cleaner, but a migration of every FK and both modules' entities, before the pool import — too late in the plan); a rename to `organisation` (breaks every query, `_aud` table and the API for no behavioural gain).

## Deferred (not in 1.3, on purpose)
- Visibility rule for RESTRICTED/CONFIDENTIAL (404 for non-team users, CO-011/PB-029): the level and team are stored now; the rule touches every query and needs its own contract.
- Activation gate on account ACTIVE (PB-014/CO-019) and tax-id validation (VWC): informational `missingForActive` only.
- New enum constants that existing exhaustive `switch` expressions would break: `BulkActionType.ARCHIVE` and `ImportKind.JOB_ORDERS/ACTIVITIES`. They are pre-approved; the backend that writes the handler adds the constant in the same PR (CRs in the hand-off).
- Roles RESEARCHER, FINANCE_VIEW, AUDITOR (CO-015/PB-028); invoice issuing; currency conversion; proposal versions and opportunities (D11).

## Deferred to post-pilot: role gating on fees and the search team (review 1.3 B2, B3)
Decision (orchestrator, on the user's scope call): 1.3 adds **no new role or permission rules**; existing role behaviour stays as it is. Two known risks are accepted for the pilot and must be closed before wider roll-out:
- **Fee → pay inference.** Placement `feeAmount` and agreement `feePercent` (with `feeBasis` = first-year cash) are readable by every consultant, so `feeAmount / feePercent` reveals a placed person's first-year cash even though `compensation` itself is restricted. Planned fix: fee fields nullable with `feesRestricted: true` below MANAGER/ADMIN, the same rule in `ExportSource` output.
- **Self-add to the team.** Any consultant can `PUT /job-orders/{id}/team` and add themselves, and team membership grants read access to placement compensation. Planned fix: team edits by the owner or MANAGER/ADMIN only (403), and `job_order_team_member.sees_compensation` (default false, MANAGER/ADMIN set it; R64) instead of membership granting pay access.

## Consequences
- All additions are optional fields, new endpoints or defaulted filters, so 1.2 clients keep working. One behaviour change: a 1.2 client moving a longlist candidate to PRESENTED without rating and rationale now gets 409; backend-pipeline updates its ITs and the seed.
- Anonymisation grows: new person-FK tables cascade, a listener deletes evaluations, notes and references, scrubs feedback text, application rationale and placement pay, and deletes client reports naming the person; the `_aud` purge list grows accordingly (ADR 0009 "Amendment for contract 1.3.0", `schema.md`).
- About 25 new enum CHECKs and 4 re-created ones (listed in `schema.md` for MigrationIT).

## Alternatives considered
- **New stages LONGLIST/SHORTLIST in `PipelineStage`**: breaks the transition table, the seed, the board and every stored value. Rejected for a derived list.
- **Hard delete with an undo window**: loses history and conflicts with the `no action` FKs on accounts. Rejected.
- **Tag table with a join table**: cleaner, but a migration of four arrays, ADR 0010 handlers and every list query. Rejected for a definition table beside the arrays.
- **Plaintext salary band column for filtering**: leaks pay to anyone with database access. Rejected for in-memory filtering.
- **Agreement and placement in `accounts`**: triggers are pipeline events (stages, placements, cancellations); keeping them with the job order avoids cross-module writes.

## Build order and owners
1. **db-engineer**: one migration per module for every table and column in `schema.md` 1.3.0, CHECKs, indexes, rank backfill, MigrationIT `ENUM_COLUMNS`, `PersonDeleteIT` FK list.
2. **backend-accounts**: archive/restore (account, person), merge orchestration, profile fields, tags, pool filters, import mapping and rollback, `ExportSource` (PEOPLE, ACCOUNTS), `PlacementCreated` listener.
3. **backend-pipeline**: archive (job order), `AccountMergeParticipant`, `TagChanged` listener, list fields, ranking, shortlist guard, client feedback, evaluations, brief, target companies, agreements, fee triggers, placements, conflict checks, client reports, `ExportSource` (JOB_ORDERS), timeline kinds.
4. **security-privacy**: export jobs (approval, watermark, expiry, audit), access-log entries for placement and report reads, anonymisation listener and `_aud` purge additions, person merge moving the new rows, share guard on reports.
5. **frontends** (after `npm run gen:api`): frontend-shell — archive menu and Archived views, merge dialog, Admin › Tags, export flow; frontend-pipeline — Longlist/Shortlist tabs, evaluation tab, Brief and Research tabs, Commercial terms, placements, report generation.
