# ADR 0011: Candidate pool, CV files and the consent engine (contract 1.2.0)

- Status: proposed for review (Wave 2b, contract 1.2.0)
- Date: 2026-10-25
- Amends: ADR 0008 (the non-AI candidate profile lives on `person` in `accounts`, not in an `ai` table)

## Context

The Product Plan (Phase 1, non-AI) moves the candidate pool (module 5) and the KVKK consent engine (module 9) into the pilot: B-01 (CV upload with Tika text, no AI parsing), B-02 (pool search), B-03 (source channel), B-04 (duplicates), B-05 (reuse and exposure history), S-01 (consent e-mail on upload), S-03 (retention, reminders, renewal, auto-anonymise), S-04 (already built). The design must keep ADR 0001 boundaries (accounts → security; pipeline → accounts; privacy → accounts, pipeline), ADR 0008 (one `person`), ADR 0009 (erasure) and ADR 0010 (views, tags). Reports, PDFs, share links and the portal (Wave 2d), AI parsing (Phase 2), volume staffing and any LinkedIn integration are out of scope.

## Decision

1. **Profile on `person` (accounts).** New columns `source_channel` (`SourceChannel`, 7 closed values), `notice_period_days`, `mobility` (`Mobility`), `compensation_enc`, `languages` (jsonb) and a `person_education` table, replaced as a whole like `person_employment`, which is reused for career history. The LinkedIn URL stays the existing plain field (no API, no scraping). Every new response field is optional, so 1.1.x clients and servers stay valid.
2. **Compensation is field-level encrypted.** One `Compensation` value (amounts, currency, period, gross/net, benefits) is encrypted with AES-256-GCM by a JPA converter that calls `security.FieldCipher` (security-privacy). Key from `FIELD_ENCRYPTION_KEY_V<k>`, version byte in the ciphertext, rotation by adding a version. It cannot be filtered or sorted, which is acceptable for the pilot. **Access:** only MANAGER/ADMIN and the relationship owner read or write it; others get `null` with `compensationRestricted: true` (403 on write). It is only in `GET /people/{id}` (VIEW-logged) and the DSR export, never in lists, search or events.
3. **Files.** `person_file` (accounts): kind CV (versioned, one current) or DOCUMENT, original name, detected type, size, SHA-256 (same file twice → 409 `DUPLICATE`), opaque `storage_key`. Bytes go through the **`FileStore` SPI in `contracts/spi`** (plain JDK). devops provides `local` (volume) now and `s3` (S3-compatible) later in `platform-app`, both encrypted at rest. Max 10 MB, types checked by Tika from the bytes, download always as an attachment with `nosniff`, logged as DOWNLOAD.
4. **Text extraction and search.** An async worker in `accounts` runs Apache Tika (no OCR, no AI) and stores `extracted_text`; a generated `tsvector` with the Turkish-stemming, accent-free `tr_unaccent` configuration and a GIN index serves `GET /people?cv=` (web-search syntax: phrases, `or`, `-word`). Only the current CV is searched. Postgres full text is enough for the pilot; OpenSearch later.
5. **Bulk upload = CV intake queue.** Without AI the server cannot create people from CVs, so `POST /cv-intake` (1–50 files) stores PENDING items, extracts text, finds e-mails, phones and LinkedIn URLs with plain patterns, and runs the duplicate check. The consultant attaches each item to a match or creates a new person. Single upload for a known person is `POST /people/{id}/files`. **ASSUMPTION:** pending items are deleted with their bytes after 14 days and are minimised on resolve; no consent e-mail goes out before a person exists. A DSR reaches pending items through `CvIntakeApi.findPendingByEmail` on `detected.emails` (export lists them, deletion discards them).
6. **Duplicates.** `POST /duplicates/check` before create (e-mail, normalised phone, normalised LinkedIn URL, name + company); only e-mail stays blocking (existing 409). Pairs found after create/update/attach and by a nightly scan go to `duplicate_candidate` (`/duplicates`, dismiss). **Merge** (`POST /people/{id}/merge`) is one transaction orchestrated by **privacy**, the only module that may call accounts, pipeline and privacy: accounts moves profile, files, contacts, links; pipeline moves applications, activities, next actions, exposures, timeline; privacy moves consent records and requests and recomputes status and retention; accounts writes `person_merge` and deletes the merged person through JPA; privacy publishes `PersonMerged`. The `_aud` purge of the survivor also covers merged ids: privacy reads them from `person_merge` before any delete (step 0 in schema.md), because on DELETE the cascade removes those rows. `version` of the survivor is required. **ASSUMPTION:** merge is MANAGER/ADMIN only.
7. **Consent engine (extends the privacy contract, no new resource).** `PersonFileUploaded` (CV) makes privacy queue the notice + consent e-mail (setting `autoSendOnCvUpload`, default on) for any person type with an e-mail, status NOT_SENT or SENT and no request younger than 7 days; REFUSED/WITHDRAWN are never re-asked automatically. Consent text versions are the existing immutable `privacy_notice`. The link is tracked by `openedAt` only; it is unreliable (mail link scanners) and never a consent signal. `ConsentRequestPurpose` RENEWAL is the renewal link (allowed while GIVEN). Reminders at `renewalReminderDays` (default 60 and 14) before `retainUntil`: RENEWAL when GIVEN, an INITIAL resend when SENT. A GIVEN answer sets `last_consent_at`, restarts the clock and publishes `RetentionRenewed` (accounts unflags the copy, pipeline closes the "Renew consent" action). Expiry still anonymises (unchanged).
8. **Sharing guard.** Shareable = consent GIVEN and not anonymised. pipeline defines an SPI `ShareGuard` in its public package; privacy implements it from its master data (the `BulkActionHandler` pattern), so pipeline gets an accurate answer without depending on privacy. **Every move into a client-facing stage** (PRESENTED, CLIENT_INTERVIEW, OFFER, PLACED: `PipelineStage.sharedWithClient()`; forward moves may skip PRESENTED) is "sharing with the client" and fails with 409 `CONSENT_REQUIRED` (`blockingItems[].reasonCode` = `ShareBlockReason`); the UI offers the existing `POST /people/{id}/consent/requests` as one-click resend. `POST /consent/share-check` answers the same question for the UI. Wave 2d reports and share links call the same SPI. Adding a person to a job order (research) needs no consent. `PATCH /applications/{id}/stage` is the only stage-changing operation; bulk `CHANGE_STATUS` excludes applications, and any later bulk stage move must apply the guards per record.
9. **Exposure history.** pipeline writes `candidate_exposure` (ids and dates) on the first move into a client-facing stage (channel PIPELINE; REPORT and SHARE_LINK reserved for 2d), backfilled from existing applications. `GET /people/{id}/exposure` returns account, job order, time and the current stage as outcome. Adding or presenting returns non-blocking `Application.warnings` (`PREVIOUSLY_PRESENTED_TO_ACCOUNT` with the exposures, `ACTIVE_IN_OTHER_PROCESS`).
10. **Off-limits.** `off_limits_rule` (accounts) targets an account or a free company name, with `OffLimitsReason`, note (no personal data), start and optional end date; CRUD on `/off-limits` (**ASSUMPTION:** write is MANAGER/ADMIN). pipeline calls `accounts.OffLimitsApi` when adding a person: a match on the person's current company (person `company` or an open employment, normalised) gives 409 `OFF_LIMITS`; rules of the job order's own account are ignored; a manager may override with a reason stored on the application. The check runs again on the first move into a client-facing stage, so a rule created later or a company change is caught (409 unless a MANAGER/ADMIN sends `offLimitsOverrideReason` with the stage move, same rules as on add). `CONSENT_REQUIRED` has no override.
11. **Talent pools and saved searches** are not a new resource: a saved search is a PEOPLE saved view (new filter keys `tag`, `sourceChannel`, `cv`, `shareable`, plus 1.1.1 `city`, `company`); a talent pool is a tag plus a SHARED view on it. `tags` now appear on `PersonSummary`.
12. **Retention basis.** New `RetentionBasis.FROM_LAST_CONSENT` (last GIVEN decision, else creation date). **ASSUMPTION:** it becomes the default (Product Plan wording), configurable as before.

## Assumptions (open client questions)

- ASSUMPTION: retention runs from the last consent (default `FROM_LAST_CONSENT`, 24 months, configurable).
- ASSUMPTION: consent is requested from every candidate, whatever the source (LinkedIn included); their lawyer may relax this, never the reverse.
- ASSUMPTION: no website application form (S-02/B-13); `SourceChannel.WEBSITE` and `ConsentChannel.WEBSITE_FORM` only record the channel.
- ASSUMPTION: client output is PDF + share link, not a portal (Wave 2d); the guard and exposure channels are ready for it.
- ASSUMPTION: CV intake items expire after 14 days; merge, off-limits writes and SHARED views are MANAGER/ADMIN.
- Out of scope: staffing mode, LinkedIn integration, AI parsing, OCR, reports/PDF/portal design.

## Consequences

- New enums: `SourceChannel`, `Mobility`, `CompensationPeriod`, `SalaryBasis`, `LanguageLevel`, `PersonFileKind`, `TextExtractionStatus`, `CvIntakeStatus`, `DuplicateMatchReason`, `DuplicateStatus`, `ConsentRequestPurpose`, `ShareBlockReason`, `ExposureChannel`, `OffLimitsReason`, `PipelineWarningCode`. Extended: `ErrorCode` (`CONSENT_REQUIRED`, `OFF_LIMITS`), `RetentionBasis`, `EntityType`. New events: `PersonFileUploaded`, `PersonMerged`, `RetentionRenewed`. New SPI: `FileStore`.
- Erasure (ADR 0009) grows: anonymisation clears the profile, deletes files and their bytes, educations and duplicate pairs; the `_aud` purge covers `person_education_aud`, `person_file_aud` and merged ids. Exposures and `person_merge` hold ids only and stay.
- Existing seed data and tests that move people to PRESENTED without consent must record consent first (QA, seed).
- Bytes outside the database need their own backup and the same region decision as the database (docs/architecture/hosting.md).

## Alternatives considered

- **Separate `candidate_profile` table owned by `ai`** (ADR 0008 plan): the fields are plain data now, and a second owner of person data would need cross-module erasure. Rejected.
- **Files as `bytea` in Postgres** (like imports): simple but bloats backups and blocks S3 later. Rejected for CVs.
- **Talent pool as its own resource with members**: duplicates tags and views, needs its own erasure rule. Rejected for the pilot.
- **Sharing guard from the consent copy on `person`**: eventually consistent, so a just-withdrawn consent could still pass. Rejected in favour of the privacy-implemented SPI.
- **Merge orchestrated in accounts with events**: cascades would delete the merged person's rows before listeners move them. Rejected.

## Review fixes (2026-10-26)

- Sharing guard and exposure apply to every move into a client-facing stage, not only PRESENTED (`PipelineStage.next()` allows forward jumps such as SOURCED → CLIENT_INTERVIEW). Off-limits is checked on add and again on the first client-facing move.
- Purge order: merged ids and file keys are collected first (schema.md step 0, ADR 0009 consequences amended to match); `person_merge.survivor_id` keeps its cascade so the FK rule and `PersonDeleteIT` stay unchanged.
- Off-limits override is also possible on the stage move (`StageChangeRequest.offLimitsOverrideReason`, MANAGER/ADMIN, 403 documented); consent has no override.
- Compensation restricted to MANAGER/ADMIN and the relationship owner; `PersonMergeRequest.version` required; `openedAt` is not a consent signal; pending intake items reachable by DSRs; basis-switch migration with `RetentionBasisMigrationIT` (schema.md, retention_settings).
